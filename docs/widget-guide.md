# Виджет «Кубик удачи»: разбор по шагам

Виджет — это маленькая страница прямо в сообщении бота. Игрок бросает три кубика, не открывая Mini App, и получает монеты. Сейчас в репозитории лежит **прототип**: правила броска, сборка HTML и бот для проверки в Telegram. С настоящими монетами и профилями он пока не связан.

Документация Telegram: <https://core.telegram.org/bots/widgets>. Замысел целиком (экономика, модификаторы, приз недели) описан в документе «Кубик удачи — архитектура».

## Шаг 0. Что получится

- Игрок пишет боту и получает сообщение с виджетом: коврик, три кубика и стакан в его скинах, рядом попытки, баланс и кнопки.
- Кнопка «Бросить» трясёт стакан и показывает, что выпало и сколько монет это принесло.
- Бросок приходит раз в 3 часа, копится не больше трёх.

## Шаг 1. Чем виджет отличается от Mini App

Mini App — обычный сайт в окне Telegram. Виджет живёт внутри пузыря сообщения, и среда у него урезанная:

| Ограничение                                | Что из него следует                                |
| ------------------------------------------ | -------------------------------------------------- |
| Сети нет: ни `fetch`, ни WebSocket         | С сервером виджет говорит только через бота        |
| HTML до 32 КБ и до 4096 байт после zlib    | Нет React и сборщика, код написан руками и коротко |
| Картинки только `data:` внутри HTML        | Коврик едет строкой пикселей и рисуется на canvas  |
| 4000 команд рисования на canvas за раз     | Слишком пёстрый коврик отклоняется при проверке    |
| Состояние — строка до 1 КБ (`chat_data`)   | Имена полей состояния однобуквенные                |
| HTML отправленного виджета изменить нельзя | При смене скина бот присылает новый виджет         |
| В проде виджеты работают только в личке    | Каждому игроку свой виджет в чате с ботом          |

## Шаг 2. Правила броска

Правила — чистые функции в `packages/shared/src/widget-roll.ts`, как у игр. Приз целиком определяется кубиками, скрытых розыгрышей нет: игрок видит кубики и может сам свериться с таблицей.

| Событие                    | Вариантов из 216 | Шанс   | Приз                      |
| -------------------------- | ---------------- | ------ | ------------------------- |
| Все разные, не подряд      | 96               | 44,44% | сумма                     |
| Пара                       | 90               | 41,67% | сумма ×2                  |
| Стрит (три числа подряд)   | 24               | 11,11% | сумма и модификатор       |
| Тройка 2-2-2, 3-3-3, 4-4-4 | 3                | 1,39%  | сумма ×5 и обычный скин   |
| Тройка 1-1-1, 5-5-5        | 2                | 0,93%  | сумма ×5 и редкий скин    |
| Три шестёрки               | 1                | 0,46%  | сумма ×5 и эпический скин |

Средний бросок приносит 16,04 монеты. Тест `packages/shared/test/widget-roll.test.ts` перебирает все 216 вариантов и проверяет и счётчики, и среднее: поменяли таблицу — тест скажет, как изменилась экономика.

**Запас бросков** не тикает в фоне. Сервер хранит два числа: сколько бросков есть и когда придёт следующий. Когда игрок пришёл, `accrueWidgetRolls` досчитывает накопившееся. Так не нужен ни cron, ни таймер на каждого игрока.

## Шаг 3. Как собирается HTML

Всё в `packages/server/src/widget/`:

- `source.ts` — исходник виджета одной строкой: стили, разметка, скрипт. Комментарии и отступы в нём для читателя, при сборке они вырезаются.
- `mat.ts` — коврик. 128×64 пикселя, один символ на пиксель, символ — номер цвета в палитре до 16 цветов. Пиксель-арт полон повторов, поэтому zlib сжимает такую строку в несколько сотен байт. Виджет рисует её отрезками: один `fillRect` на отрезок одинаковых пикселей в строке.
- `build.ts` — `buildWidgetHtml(skins, links)` подставляет вместо `__CFG__` скины игрока и ссылки кнопок, меряет результат и **бросает ошибку**, если он не влезает в лимиты. Отправить Telegram слишком большой виджет и получить отказ в бою хуже, чем упасть при сборке.

Сейчас виджет с ковриком по умолчанию занимает около 3 КБ из 4 после сжатия. Около 2,6 КБ — код и разметка, остальное — коврик. Значит, на новый код осталось примерно 1 КБ: каждую новую кнопку придётся взвешивать.

## Шаг 4. Разговор виджета с ботом

```
виджет                         Telegram                       бот
  │  TelegramWidget.request('r')  │                            │
  ├──────────────────────────────►│  update: widget_query      │
  │                               ├───────────────────────────►│ бросает кубики,
  │                               │  answerWidgetQuery(data)   │ считает монеты
  │  Promise → {result}           │◄───────────────────────────┤
  │◄──────────────────────────────┤  editMessageWidgetData     │
  │  событие chatDataChanged      │◄───────────────────────────┤
  │◄──────────────────────────────┤                            │
```

- **Запрос.** Виджет шлёт строку до 64 байт, у нас это `r` (roll). Вызывать `request()` можно только внутри обработчика нажатия. В `widget_query` бот получает `from` — так он знает, какой игрок нажал. Подделать `from` игрок не может, его ставит Telegram.
- **Ответ.** Бот обязан ответить за 15 секунд методом `answerWidgetQuery`. Ответ — JSON до 1 КБ: кубики, событие, монеты и новый запас (`WidgetRollAnswer` в `demo.ts`), либо `{"e":"NO_ROLLS"}`. Его видит только тот виджет, который спросил.
- **Состояние.** Ответ нигде не хранится: закроет игрок чат — и его нет. Поэтому бот ещё и кладёт актуальное состояние в `chat_data` методом `editMessageWidgetData`. Его виджет читает при каждом открытии.

Кубики бросает сервер. Виджет ничего не решает: он показывает ответ и досчитывает таймер между ответами, чтобы цифры не стояли на месте. Даже если игрок подделает таймер у себя, бросок ему выдаёт сервер.

Кнопки «Позвать друга», «+1 за рекламу» и «Найти игру» — это ссылки `https://t.me/…`, которые открывает `openTelegramLink`. Рекламу и оплату внутри виджета показать нельзя (сети нет), поэтому они живут в Mini App.

## Шаг 5. Посмотреть в браузере

```
pnpm --filter @gamedeck/server widget:preview
```

Откроется <http://localhost:5180>: тот же HTML плюс подмена `window.TelegramWidget`, которая шлёт бросок на локальный сервер. Чтобы не ждать три часа, задайте интервал: `WIDGET_ROLL_INTERVAL_SEC=20`.

Превью показывает вёрстку и логику. Оно **не** проверяет среду Telegram: движок QuickJS, лимиты и тему клиента. Это видно только в настоящем клиенте.

## Шаг 6. Проверить в Telegram

Нужен **отдельный тестовый бот**, не боевой: прототип отвечает виджетом на любое сообщение, а игроки боевого бота этого видеть не должны.

1. Создайте бота у @BotFather (`/newbot`) и скопируйте токен.
2. Запустите на своей машине:

   ```
   WIDGET_BOT_TOKEN=<токен> WIDGET_ROLL_INTERVAL_SEC=60 pnpm --filter @gamedeck/server widget:bot
   ```

   В PowerShell переменные задаются так: `$env:WIDGET_BOT_TOKEN="<токен>"`.

3. Напишите боту что угодно — придёт виджет.

Бот (`dev-bot.ts`) получает обновления long polling: сам спрашивает Telegram методом `getUpdates`, поэтому ему не нужны ни домен, ни открытый порт. Нужен только доступ к `api.telegram.org`. Игроков он держит в памяти: перезапустили — баланс прототипа сбросился.

Токен читается из `WIDGET_BOT_TOKEN`, а не из `BOT_TOKEN`, чтобы прототип нельзя было случайно запустить от имени боевого бота.

## Что дальше

Прототип отвечает на вопрос «влезает ли стол со скинами в 4 КБ и удобно ли это в чате». Чтобы виджет стал частью игры, остаётся:

- связать бросок с профилем игрока по `telegram_id` и начислять монеты через `changeCoins`;
- хранить запас бросков, выпавшие скины и модификаторы в базе;
- принимать обновления в основном сервере (вебхук вместо long polling) и решить, как сервер в РФ достучится до `api.telegram.org`;
- перевести коврики магазина из PNG в формат `MatSkin`.
