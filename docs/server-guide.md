# Как устроен сервер GameDeck: разбор по шагам

Этот документ объясняет, из чего состоит сервер, зачем нужна каждая часть и как они связаны. Читать удобнее сверху вниз: каждый шаг опирается на предыдущий.

## Шаг 0. Сколько серверов нужно

**Один процесс Node.js.** В нём Fastify обслуживает HTTP, а Socket.IO на том же порту держит WebSocket-соединения и для лобби, и для игры.

Почему не два сервера («комнаты» отдельно, «игра» отдельно):

- Комната и партия это одно состояние: кто за столом, кто хост, чей ход. Разнесёте по процессам, и их придётся синхронизировать через Redis или очередь. Сразу появятся гонки: хост кикнул игрока ровно в момент его броска, и два сервера видят разную правду.
- Нагрузка у игр на костях мизерная. Один процесс держит тысячи сокетов.
- Один процесс проще запускать на TRASHCAN, отлаживать и показывать на собеседовании.

**Когда разделять.** Когда одной машины перестанет хватать или появится БД с рейтингом и монетами. Тогда запускают несколько одинаковых процессов за балансировщиком. Каждая комната живёт целиком на одном процессе (sticky-сессии), а общие данные (профили, монеты, рейтинг) лежат в Postgres, список комнат и межпроцессные события идут через Redis (`@socket.io/redis-adapter`). Код уже разложен под это: правила игр не знают о сети, комнаты не знают о сокетах.

## Шаг 1. Монорепозиторий

```
packages/
  shared/   контракт клиент ↔ сервер и правила игр
  server/   Fastify + Socket.IO
```

`pnpm-workspace.yaml` говорит pnpm, что в `packages/*` лежат пакеты. Сервер подключает общий пакет как обычную зависимость:

```json
"dependencies": { "@gamedeck/shared": "workspace:*" }
```

**Зачем `shared`.** Клиент и сервер должны одинаково понимать, какие события бывают и какие у них данные. Описываем это один раз, и TypeScript ругается с обеих сторон, если кто-то разошёлся с контрактом.

**Трюк с условием `source`.** В `packages/shared/package.json`:

```json
"exports": {
  ".": {
    "source": "./src/index.ts",
    "types": "./dist/index.d.ts",
    "default": "./dist/index.js"
  }
}
```

В разработке (`tsx --conditions=source`), в тестах (`vitest.config.ts`) и при проверке типов (`customConditions` в `tsconfig.base.json`) импорт `@gamedeck/shared` ведёт прямо в исходники `.ts`, без сборки. В продакшене Node берёт собранный `dist/index.js`.

## Шаг 2. Контракт событий (`shared/src/protocol.ts`)

Socket.IO позволяет типизировать события. Описываем, что шлёт клиент и что шлёт сервер:

```ts
export interface ClientToServerEvents {
  'room:create': (input: CreateRoomInput, ack: Ack<RoomView>) => void;
  'room:join':   (input: JoinRoomInput,   ack: Ack<RoomView>) => void;
  'game:move':   (input: MoveInput,       ack: Ack<RoomView>) => void;
  // ...
}

export interface ServerToClientEvents {
  session: (session: SessionInfo) => void;
  'room:state': (room: RoomView) => void;
  'room:kicked': (info: { code: string }) => void;
}
```

**Что такое `ack`.** Это ответ сервера на конкретный запрос, как `return` у функции. Клиент пишет:

```ts
const result = await socket.emitWithAck('room:join', { code: 'K7M2Q', name: 'Лёха' });
if (!result.ok) showError(result.error.message);
```

Ответ всегда одной формы: `{ ok: true, data }` или `{ ok: false, error: { code, message } }`. Клиенту не нужно гадать, как выглядит ошибка.

**Модель «сервер шлёт всё состояние».** После любого изменения сервер рассылает всем в комнате `room:state` с полным `RoomView`. Это проще, чем рассылать маленькие события («Боб бросил 4») и собирать состояние на клиенте: клиент просто перерисовывает стол. Для 6 игроков объём данных крошечный.

`RoomView` это и есть серверное описание стола: у каждого игрока есть `seat` (0..5), клиент поворачивает стол так, чтобы своё место было снизу.

## Шаг 3. Валидация входящих данных (`shared/src/schemas.ts`)

TypeScript проверяет типы только при сборке. По сети может прийти что угодно: старый клиент, баг или злоумышленник. Поэтому каждое входящее событие проходит через zod:

```ts
export const joinRoomSchema = z.object({
  code: roomCodeSchema,          // 5 символов, приводится к верхнему регистру
  name: playerNameSchema,        // 1..24 символа, обрезаются пробелы
  password: z.string().max(32).optional(),
});

export type JoinRoomInput = z.input<typeof joinRoomSchema>;
```

Тип выводится из схемы, поэтому схема и тип не разъедутся никогда.

## Шаг 4. Правила игры как чистые функции (`shared/src/games/`)

Каждая игра реализует общий интерфейс:

```ts
interface GameModule<State, Move> {
  start(playerIds): State;
  currentPlayer(state): string | null;
  applyMove(state, playerId, move, rng): State;  // ошибка, если ход недопустим
  removePlayer(state, playerId): State;
  winner(state): string | null;
}
```

Функции не трогают сеть, не читают время и не мутируют входное состояние: получили состояние и ход, вернули новое состояние. Отсюда три плюса:

1. Правила тестируются за миллисекунды, без сервера (`shared/test/dice-high.test.ts`).
2. Новая игра (перудо, тысяча, покер на костях) это новый модуль и строчка в реестре `games`. Комнаты и стол не меняются.
3. Случайность передаётся параметром `rng`. В тестах подставляем «кубик, который выдаёт 6, 6, 3, 5» и проверяем переброс при ничьей детерминированно.

Логика «Броска кубика»: все в `contenders` бросают по очереди. Когда раунд закончен, ищем максимум. Один лидер это победитель, несколько лидеров это новый раунд, где `contenders` = только лидеры.

## Шаг 5. Комната (`server/src/rooms/room.ts`)

`Room` хранит игроков, хоста, настройки и текущую партию, и проверяет права:

```ts
startGame(byId: string): void {
  this.assertHost(byId);                       // только хост
  if (this.status === 'playing') throw ...     // не во время игры
  const order = [...this.players.values()]
    .sort((a, b) => a.seat - b.seat)           // ходы по часовой стрелке
    .map((p) => p.id);
  this.game = { module, state: module.start(order) };
  this.status = 'playing';
}
```

Что важно:

- Статусы: `lobby` → `playing` → `finished`. Из `finished` хост может начать реванш.
- Во время игры войти нельзя, настройки менять нельзя.
- Ушёл хост, и хостом становится следующий по месту.
- Ушёл игрок посреди партии, и он выбывает из очереди. Остался один, и он победил.
- Пароль наружу не отдаётся, в `RoomView` только `hasPassword`.

`RoomManager` это реестр комнат: создаёт короткие коды (без 0/O и 1/I, чтобы их легко диктовать), знает, кто в какой комнате, удаляет пустые комнаты.

## Шаг 6. Кто подключился: сессии (`server/src/players/player-service.ts`)

Сокет живёт до первого обрыва связи, а игрок должен пережить перезагрузку вкладки. Поэтому:

1. При первом подключении сервер выдаёт `{ token, playerId }` событием `session`.
2. Клиент сохраняет `token` (например, в `localStorage`) и при следующем подключении передаёт его:

```ts
const socket = io({ auth: { token: localStorage.getItem('token') } });
socket.on('session', ({ token }) => localStorage.setItem('token', token));
```

3. Сервер узнаёт игрока и возвращает его в комнату, на то же место.

Сессии хранятся в базе (подробности в [database-guide.md](database-guide.md)), поэтому переживают перезапуск сервера.

Когда подключим Telegram Mini App, здесь появится проверка подписи `initData`: игрок будет находиться по `telegram_id`, а не только по токену.

## Шаг 7. Обработчики событий (`server/src/socket/handlers.ts`)

Этот слой тонкий: распарсить вход, вызвать комнату, разослать новое состояние. Всю обработку ошибок берёт на себя обёртка `handle`:

```ts
socket.on('game:move', handle(([input]) => {
  const room = requireRoom(rooms, playerId);
  room.move(playerId, moveSchema.parse(input), rng);
  broadcast(room);
  return room.toView();
}));
```

`handle` ловит исключения и превращает их в `{ ok: false, error }`. Ошибки правил (`NOT_YOUR_TURN`) уходят клиенту как есть, ошибки zod становятся `BAD_REQUEST`, а неожиданные пишутся в лог, наружу уходит только общий текст.

**Каналы Socket.IO.** У Socket.IO есть «комнаты» (здесь назовём их каналами, чтобы не путать с игровыми):

- `room:K7M2Q` все сокеты игроков этой комнаты, туда рассылаем `room:state`;
- `player:<id>` все вкладки одного игрока, туда шлём `room:kicked`.

**Обрыв связи.** Когда закрылась последняя вкладка игрока, он помечается `connected: false`, и все видят это на столе. Если он не вернулся за `DISCONNECT_GRACE_MS` (по умолчанию 60 секунд), он выходит из комнаты. Так партия не зависает навсегда из-за ушедшего игрока.

## Шаг 8. Сборка приложения (`server/src/app.ts`, `index.ts`)

```ts
const app = Fastify({ logger });
const io = new Server(app.server);   // Socket.IO на том же http-сервере
registerSocketHandlers({ io, rooms, sessions, rng, ... });
registerHttpRoutes(app, rooms);
```

`buildApp()` только собирает приложение, а `index.ts` его запускает. Благодаря этому тесты поднимают настоящий сервер на случайном порту (`port: 0`) и подключают настоящих клиентов (`server/test/socket.test.ts`).

Бросок делается через `crypto.randomInt`, а не `Math.random`: его нельзя предсказать по предыдущим броскам. Для игры на монеты это важно.

HTTP-маршруты:

| Маршрут | Зачем |
| --- | --- |
| `GET /api/health` | Проверить, что сервер жив (пригодится для systemd и мониторинга) |
| `GET /api/rooms/:code` | Превью комнаты по ссылке-приглашению: игра, ставка, сколько мест занято, есть ли пароль |

`index.ts` слушает `SIGINT`/`SIGTERM` и закрывает сервер аккуратно: сначала сокеты, потом HTTP.

## Шаг 9. Запуск и проверка

```bash
pnpm install
pnpm dev          # сервер с перезапуском при изменениях, http://0.0.0.0:3000
pnpm test         # тесты: правила, комнаты, база, сквозные через сокеты
pnpm build && pnpm start
```

Быстрая проверка руками:

```bash
curl http://localhost:3000/api/health
# {"ok":true,"rooms":0}
```

С телефона в Tailscale: `http://<tailscale ip TRASHCAN>:3000/api/health`.
