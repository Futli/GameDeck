# База данных GameDeck: что, зачем и как работает

Продолжение [server-guide.md](server-guide.md). Здесь разобрано, как сервер хранит игроков, рейтинг, историю партий, монеты, предметы и покупки за Telegram Stars.

## Шаг 1. Что храним в базе, а что в памяти

| Где | Что | Почему |
| --- | --- | --- |
| Память процесса | Комнаты, партии в процессе, очередь ходов | Живут минуты, меняются на каждый бросок; терять их при перезапуске не страшно |
| База | Игроки, сессии, рейтинг, история партий, монеты, предметы, платежи | Должны пережить перезапуск, за них платят деньги |

Правило простое: в базу пишем **итог** (партия закончилась, покупка прошла), а не каждый промежуточный шаг. Игра остаётся быстрой, а база получает пару запросов в минуту.

## Шаг 2. Выбор: PostgreSQL + Drizzle ORM

- **PostgreSQL** — стандарт для такого проекта: транзакции, внешние ключи, `CHECK`-ограничения. Деньги (пусть и виртуальные) без транзакций хранить нельзя.
- **Drizzle ORM** — схема описывается на TypeScript, и типы запросов выводятся из неё. Опечатка в имени колонки ловится при сборке, а не в продакшене. При этом запросы выглядят почти как SQL, поэтому видно, что реально уходит в базу.
- **PGlite** — настоящий Postgres, скомпилированный в WebAssembly и запущенный внутри Node. Ставить ничего не нужно: если `DATABASE_URL` не задан, сервер сам создаёт базу в `packages/server/data/pglite`. В тестах он работает в памяти.

Выбор драйвера в `src/db/client.ts`:

```ts
if (/^postgres(ql)?:\/\//.test(url)) {
  const pool = new pg.Pool({ connectionString: url });   // настоящий Postgres
  ...
}
const client = new PGlite(url);                          // встроенный, файлы или memory://
```

Код запросов одинаковый для обоих вариантов, поэтому переход с PGlite на Postgres — это одна переменная окружения.

**Как перейти на PostgreSQL на TRASHCAN:**

```bash
docker compose up -d
DATABASE_URL=postgres://gamedeck:gamedeck@localhost:5432/gamedeck pnpm start
```

В `docker-compose.yml` порт открыт только на `127.0.0.1`, так что из Tailscale базу не видно, только сам сервер.

## Шаг 3. Схема (`src/db/schema.ts`)

11 таблиц в трёх группах.

### Игроки

```
players            id, telegram_id, display_name, coins, created_at, last_seen_at
sessions           token_hash → player_id
```

- `telegram_id` пока пустой. Когда подключим Mini App, игрок будет находиться по нему.
- В `sessions` хранится **SHA-256 токена**, а не сам токен. Если базу украдут, войти за игрока по ней нельзя: так же хранят пароли.
- `coins` защищён ограничением `CHECK (coins >= 0)`. Даже баг в коде не сможет увести баланс в минус: база откажет.

### Рейтинг и статистика

```
player_game_stats  (player_id, game_id) → rating, peak_rating, games_played, wins
matches            id, game_id, room_code, stake, winner_id, started_at, finished_at
match_players      (match_id, player_id) → seat, place, rating_before, rating_after
```

- Рейтинг **отдельный для каждой игры**: сильный игрок в перудо не обязательно силён в покере на костях.
- В `match_players` записан рейтинг до и после. Из этого строится график рейтинга и экран «последние партии», ничего не пересчитывая.
- Индекс `(game_id, rating DESC)` делает таблицу лидеров быстрой даже на миллионе строк.

### Монетизация

```
items              id, kind, name, rarity, price_coins, price_stars, asset, is_default, is_active
coin_packs         id, title, price_stars, coins
player_items       (player_id, item_id) → source, acquired_at        — инвентарь
player_equipment   (player_id, slot) → item_id                       — что надето
coin_transactions  player_id, amount, balance_after, reason, ref_id  — журнал монет
stars_payments     telegram_charge_id (UNIQUE), product, stars, status
```

- `kind` предмета совпадает со слотом: `mat` (коврик 128×64), `dice` (скин кубика), `frame` (рамка аватара), `emote` (эмоция). Новый вид предметов — новое значение, без миграции.
- Первичный ключ `(player_id, item_id)` не даёт получить один предмет дважды.
- У предмета две цены: за монеты и за Stars. `null` значит «так не продаётся». Легендарный коврик можно сделать только за Stars, обычный — только за монеты.
- `is_active = false` снимает предмет с продажи, но у купивших он остаётся.

## Шаг 4. Миграции

Схема в TypeScript — это описание того, какой база **должна быть**. Миграции — это SQL, который делает её такой.

```bash
# поменяли schema.ts → генерируем SQL
pnpm db:generate
# появится packages/server/drizzle/0001_....sql — его коммитим
```

При старте сервер сам применяет новые миграции (`migrate()` в `openDatabase`). Drizzle помнит, какие уже применены, в служебной таблице `drizzle.__drizzle_migrations`. Поэтому обновление на TRASHCAN — это `git pull && pnpm build && pnpm start`, без ручного SQL.

Посмотреть данные глазами: `pnpm db:studio` откроет Drizzle Studio в браузере (нужен `DATABASE_URL` с Postgres).

## Шаг 5. Как игрок появляется в базе

`PlayerService.resolveSession` вызывается при каждом подключении сокета:

1. Токен есть и его хэш найден → это старый игрок, обновляем `last_seen_at`.
2. Иначе регистрация **в одной транзакции**:

```ts
await this.db.transaction(async (tx) => {
  const [player] = await tx.insert(players).values({}).returning();
  await tx.insert(sessions).values({ tokenHash: hashToken(token), playerId: player.id });
  // бесплатные предметы (is_default) → в инвентарь и сразу надеть
  // стартовые монеты → через changeCoins, с записью в журнал
});
```

Если любой шаг упадёт, откатится всё: не будет игрока без сессии или с монетами, но без записи в журнале.

Имя игрока сохраняется при создании комнаты или входе в неё, чтобы оно было в таблице лидеров.

## Шаг 6. Как партия попадает в рейтинг

1. Комната замечает победителя и собирает итог (`MatchResult`): кто на каком месте. Места даёт сама игра через `standings()`, потому что только она знает правила. Для «Броска кубика» выше тот, кто дольше продержался в перебросах, а среди выбывших в одном раунде — у кого больше выпало. Кто ушёл посреди партии, получает последнее место.
2. Обработчик сокетов сразу рассылает игрокам `room:state` с победителем и **параллельно** вызывает `stats.recordMatch()`. Игра не ждёт базу.
3. `recordMatch` в одной транзакции:
   - создаёт строки статистики для новичков (рейтинг 1000);
   - читает текущие рейтинги с `SELECT ... FOR UPDATE`, чтобы две одновременные партии одного игрока не затёрли друг друга;
   - считает новый рейтинг, пишет `matches`, `match_players` и обновляет `player_game_stats`.
4. Клиентам приходит событие `match:recorded` с `ratingBefore`/`ratingAfter`, и можно показать «+16».

### Рейтинг Elo на несколько игроков (`src/stats/elo.ts`)

Классический Elo рассчитан на дуэль. Партию на N игроков считаем как набор дуэлей «каждый с каждым»:

```ts
expected = 1 / (1 + 10 ** ((other.rating - me.rating) / 400));   // шанс выиграть у other
actual   = me.place < other.place ? 1 : me.place === other.place ? 0.5 : 0;
delta   += (K / (N - 1)) * (actual - expected);
```

- Победа над сильным даёт больше очков, чем над слабым.
- K делится на N−1, чтобы партия на шестерых двигала рейтинг так же, как дуэль, а не в 5 раз сильнее.
- Сумма изменений у всех игроков около нуля: рейтинг не «печатается» из воздуха.

Пример: двое по 1000, победитель получает 1016, проигравший 984.

## Шаг 7. Монеты: журнал и одна функция для баланса

Баланс меняется только через `changeCoins` (`src/db/wallet.ts`):

```ts
const [row] = await tx
  .update(players)
  .set({ coins: sql`${players.coins} + ${amount}` })
  .where(and(eq(players.id, playerId), gte(sql`${players.coins} + ${amount}`, 0)))
  .returning({ coins: players.coins });
if (!row) throw new AppError('INSUFFICIENT_COINS', 'Недостаточно монет');
await tx.insert(coinTransactions).values({ playerId, amount, balanceAfter: row.coins, reason, refId });
```

Зачем так:

- Проверка «хватает ли денег» и списание — **один** `UPDATE`. Если игрок нажмёт «купить» в двух вкладках одновременно, второй запрос просто не найдёт строку с достаточным балансом. Вариант «сначала SELECT баланса, потом UPDATE» тут бы сломался.
- Каждое движение монет пишется в `coin_transactions` с причиной (`bonus`, `item_purchase`, `stars_purchase`, позже `match_win`, `match_stake`, `referral`). На вопрос игрока «куда делись монеты» всегда есть ответ, а баланс можно сверить с суммой журнала.

## Шаг 8. Магазин (`src/shop/`)

**Каталог в коде.** Предметы и паки монет описаны в `catalog.ts`. При старте сервер делает `INSERT ... ON CONFLICT DO UPDATE`: новые предметы добавляются, у старых обновляются цены. Изменения цен проходят через git и ревью, а не правятся руками в базе.

**Покупка за монеты** (`buyWithCoins`), всё в одной транзакции:

1. Предмет существует, продаётся и у него есть цена в монетах.
2. Вставляем строку в инвентарь. Если она уже есть (PK), значит предмет куплен, ошибка `ALREADY_OWNED`.
3. Списываем монеты через `changeCoins`. Не хватило — транзакция откатывается вместе с предметом.

**Экипировка** (`equip`): проверяем, что предмет есть в инвентаре, и пишем его в слот его вида. Один слот — один предмет.

**Покупка за Stars** (`applyStarsPayment`). Сама оплата пойдёт через Telegram-бота: бот выставляет инвойс в валюте `XTR`, Telegram присылает `successful_payment` с `telegram_payment_charge_id`. Метод уже готов принять это событие:

- Сначала вставляем платёж в `stars_payments`. `telegram_charge_id` уникален, поэтому если Telegram пришлёт то же событие повторно (так бывает), второй раз ничего не начислится.
- Сверяем сумму в Stars с ценой товара. Не совпала — откат и ошибка.
- Начисляем монеты (`changeCoins`, причина `stars_purchase`) или выдаём предмет.

Осталось подключить самого бота, это следующий шаг вместе с авторизацией через Telegram.

## Шаг 9. HTTP API

| Маршрут | Доступ | Что возвращает |
| --- | --- | --- |
| `GET /api/players/:id` | все | Профиль: имя, рейтинг и статистика по играм, 10 последних партий, надетые предметы |
| `GET /api/leaderboard?game=dice-high&limit=20` | все | Топ по рейтингу (только сыгравшие хотя бы раз) |
| `GET /api/shop/catalog` | все | Предметы и паки монет в продаже |
| `GET /api/me/inventory` | по токену | Баланс, предметы, что надето |
| `POST /api/shop/buy` `{ itemId }` | по токену | Покупка за монеты, в ответе новый инвентарь |
| `POST /api/me/equip` `{ itemId }` | по токену | Надеть предмет, в ответе новый инвентарь |

«По токену» значит заголовок `Authorization: Bearer <token>`, тот же токен, что приходит в событии `session`:

```bash
curl -X POST http://localhost:3000/api/shop/buy \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"itemId":"mat-wood"}'
```

Ошибки всегда одной формы: `{ "error": "INSUFFICIENT_COINS", "message": "Недостаточно монет" }`, со статусом 400, 401 или 404.

## Шаг 10. Тесты

```bash
pnpm test
```

- `elo.test.ts` — формула рейтинга.
- `room.test.ts` — итог партии и места, включая ушедших.
- `services.test.ts` — настоящие запросы на PGlite: регистрация, рейтинг, таблица лидеров, покупки, нехватка монет, повторный платёж Stars, откат неверного платежа.
- `socket.test.ts` — сквозной: партия через сокеты заканчивается событием `match:recorded` с новым рейтингом.

PGlite стартует несколько секунд, поэтому одна база в памяти создаётся на тестовый файл, а каждый тест работает со своими новыми игроками.
